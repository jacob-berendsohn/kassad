# Roadmap — Kassad 0.1.0

## Goal

Publish `Kassad`, `Kassad.Abstractions`, `Kassad.TypeSafe`, and `Kassad.AspNetCore` at version `0.1.0` on nuget.org, targeting `net8.0` and `net10.0`, with: a TypeSafe System One client whose wire handling is verified against recorded live responses; a policy engine that batches one request per stage and resolves confidence-gated verdicts; inbound middleware and a provider-side `DelegatingHandler` proven by integration tests; and a README "Numbers" table generated by the eval harness from at least two public inbound datasets, reporting precision/recall per threshold, calibration, p50/p95 latency, and cost per 1k checks.

## Definition of Done

- [ ] `dotnet build -c Release` completes with zero warnings on `ubuntu-latest` and `windows-latest` in CI
- [ ] `dotnet test -c Release` is green in CI; no unit test requires network access or `TYPESAFE_API_KEY`
- [ ] Tests tagged `Category=Live` pass against `api.typesafe.ai` in the `live` CI job
- [ ] `tests/Kassad.TypeSafe.Tests/Fixtures/*.json` are recorded from live responses (a `recorded_at` field is present in each)
- [ ] `PublicAPI.Shipped.txt` is populated for all four `src/` projects and `RS0016`/`RS0017` are errors (no `WarningsNotAsErrors` entry remains)
- [ ] `AnalysisLevel` is `latest-recommended` and the build is clean
- [ ] `git tag v0.1.0` triggers `release.yml`, which publishes all four `.nupkg` + `.snupkg` via Trusted Publishing without manual steps
- [ ] Each package on nuget.org shows the README, Apache-2.0 license expression, SourceLink, and both TFMs
- [ ] `samples/Kassad.Sample.ChatApi` runs against the live API and the README's `curl` example returns a 403 for the injection prompt and 200 for a benign one
- [ ] `WebApplicationFactory`-based tests cover middleware reject/pass/oversized paths; handler tests cover inbound reject, outbound reject, streaming pass-through
- [ ] `eval/results/` contains committed JSON for ≥ 2 inbound datasets, and the README "Numbers" table is generated from them by `kassad-eval report` (no hand-typed numbers)
- [ ] `PROJECT_CONTEXT.md` open questions marked resolved for everything this roadmap closes; `CHANGELOG.md` has a `0.1.0` section

- **TypeSafe early-access API key.** 0.3, 1.3, 2.4, and all of Phase 4 depend on it. Default assumption: one key, rate limits unknown. If Phase 4 hits limits, evaluate stratified samples (≥ 500 rows per dataset) and say so in the report.

- **TypeSafe pricing for the cost column.** 4.2 depends on it. Default assumption: use the publicly quoted per-token rate labeled "quoted, verify"; do not block the table on official pricing.
- **Dataset licenses permit redistribution of derived metrics.** 4.1. Default assumption: yes for JailbreakBench, deepset prompt-injections, ToxicChat (research licenses); raw data is never committed regardless.

## Out of scope

- A standalone OpenAI-compatible reverse proxy (`kassad-proxy`). Separate initiative after 0.1.
- A Python port or any non-.NET SDK.
- An LLM-backed fallback `IDecisionModel` (`Kassad.LlmJudge`). Design reference noted in `Docs/research/typesafe-api-notes.md`; not built here.
- YAML policy files or any second policy format.
- Token-level evaluation of streaming responses. 3.4 produces a design note only.
- Composite policies (`all_of` / `any_of`), per-policy model selection, threshold expressions.
- A dashboard, UI, or hosted service of any kind.
- Reserved-prefix application for `Kassad.*` on nuget.org (requires published packages first; do after 0.1.0).
- Eval datasets beyond inbound + one grounding set. Outbound/tool-call datasets are a 0.2 concern.

## Phases

Phases 0 → 1 → 2 are strictly sequential. Phase 3 and Phase 4 depend on Phase 1 and can run in parallel with Phase 2 and with each other, except 4.4 which depends on everything.

### Phase 1 — Engine verified end-to-end

**End state.** The policy loader and engine are covered for every branch in the spec, the engine can bound its own latency, and the sample app produces correct verdicts against the live API.

**Success markers.** `PolicySet` tests enumerate every validation rule in `Docs/specs/policy-file-format.md`; the sample's `curl` examples behave as the README states; engine tests cover the timeout path.

##### 1.1 — Policy loader covered rule-for-rule

- **Goal.** One test per validation rule in the spec, plus parser leniency (comments, trailing commas, case-insensitive keys).
- **Deliverables.** `PolicyDocumentTests.cs` with a `Theory` per rule using inline JSON; error-message assertions that reference the field name; the spec updated if a rule turned out to be missing from the code; fix for a known bug from the 2026-09-17 review: `PolicyDocument.Parse` records the validation error for an `actions` entry whose `action` is missing or `null`, then still dereferences it while building the `Policy`, so callers get `InvalidOperationException`/`NullReferenceException` instead of `PolicyValidationException` (skip policy construction for any entry that produced errors).
- **Verification.** Every bullet under "Validation" in `Docs/specs/policy-file-format.md` maps to a named test; `"actions": { "x": {} }` and `"actions": { "x": null }` both throw `PolicyValidationException` naming the option; coverage report shows `PolicyDocument.cs` and `PolicySet.cs` ≥ 95% line coverage.
- **Depends on.** 0.2.

##### 1.2 — Engine latency budget

- **Goal.** Let operators cap how long a stage waits on the model, with the overrun handled by each policy's `on_error`.
- **Deliverables.** `EvaluationOptions { TimeSpan? Budget }` on `GuardrailEngine` (constructor or `IOptions`); a linked `CancellationTokenSource`; budget overrun yields error verdicts with reason `"budget exceeded"` while the caller's own cancellation still propagates; `StageResult.BudgetExceeded` flag; tests using a `FakeDecisionModel` that delays.
- **Verification.** Test: 50 ms budget, 500 ms fake → result in < 100 ms with `BudgetExceeded == true`, fail_closed policies Block, fail_open Allow. Test: caller cancels → `OperationCanceledException` propagates.
- **Depends on.** 0.2.

##### 1.3 — Sample runs against the live API

- **Goal.** The reference sample behaves as documented with real verdicts.
- **Deliverables.** Any fixes needed for the sample; README `curl` commands verified; a `samples/README.md` with the expected JSON for a benign and an injection prompt (values redacted to ranges, since they'll drift).
- **Verification.** `TYPESAFE_API_KEY=... dotnet run --project samples/Kassad.Sample.ChatApi` then the two `curl`s from the README return 200 and 403 respectively; log output shows one `Kassad Inbound outcome` line per request with two policy lines.
- **Depends on.** 0.3, 1.1.

### Phase 2 — ASP.NET Core integration proven

**End state.** Middleware and handler have integration tests for every branch in `Docs/specs/rejection-response.md`, and inbound state is extracted structurally from known provider request shapes rather than passed as a raw body.

**Success markers.** `Kassad.AspNetCore.Tests` project exists and is green; the handler screens the user turn of an OpenAI-shaped request, not the whole JSON envelope.

##### 2.1 — Middleware integration tests

- **Goal.** Exercise `KassadInboundMiddleware` through a real pipeline.
- **Deliverables.** `tests/Kassad.AspNetCore.Tests/` (xunit + `Microsoft.AspNetCore.Mvc.Testing`, versions added to CPM) using `FakeDecisionModel`; tests for: block → 403 problem+json without `policies`; block with `IncludePolicyIdsInResponse` → `policies` present; review → 200 with `Kassad-Outcome: review` and `GetKassadInboundResult()` populated; non-text content type → engine not called; oversized fail_closed → 413; oversized fail_open → engine not called, 200; `RejectAt = Review` → review rejected. Fix for a known bug from the 2026-09-17 review: `KassadInboundMiddleware.WriteRejectionAsync` sets `application/problem+json` and then calls the two-argument `WriteAsJsonAsync`, which resets `Content-Type` to `application/json; charset=utf-8`; use the overload that takes a `contentType`.
- **Verification.** All listed tests exist and pass; the 403 and 413 tests assert `Content-Type` starts with `application/problem+json`; middleware file coverage ≥ 90%.

##### 2.2 — Handler integration tests

##### 2.3 — Structured state extraction

### Phase 3 — Remaining stages usable, observability in place

**End state.** `tool_call` and `grounding` have typed helpers so callers don't hand-roll state objects; the engine emits OpenTelemetry-compatible traces and metrics; the two known handler gaps are closed or explicitly designed.

**Success markers.** A caller can write `await engine.EvaluateToolCallAsync(intent, schema, args)`; an OTel collector receives one activity per stage evaluation with verdict tags.

##### 3.1 — Typed tool-call and grounding helpers

- **Goal.** Make the two code-only stages ergonomic.
- **Deliverables.** `ToolCallState(string UserIntent, string ToolName, string ToolSchemaJson, string ArgumentsJson)` and `GroundingState(string Claim, string SourcePassage, string? SourceId)` records in `Kassad.Abstractions`; `GuardrailEngineExtensions.EvaluateToolCallAsync` / `EvaluateGroundingAsync`; sample policies for both stages added to `kassad.policies.json` (commented as illustrative); README "Stages" table updated.
- **Verification.** Unit tests show the records serialize into the `state` object with the documented field names; a live test runs one tool-call and one grounding policy and gets typed answers back.
- **Depends on.** 1.2.

##### 3.2 — Oversized-body pass-through in the handler

- **Goal.** Make `OversizedBodyBehavior = fail_open` work in the handler instead of throwing.
- **Deliverables.** Bounded read that stops at `MaxBodyBytes + 1` without consuming the rest; on overflow with fail_open, the original content is re-attached (buffered prefix + remaining stream) and sent unevaluated with a warning; `PROJECT_CONTEXT.md` caveat removed.
- **Verification.** Handler test: 2 MiB request with 1 MiB limit and fail_open → provider receives the full 2 MiB byte-identically; fail_closed → 413 and provider not called.
- **Depends on.** 2.2.

##### 3.3 — OpenTelemetry traces and metrics

- **Goal.** Let operators see verdict rates and latency without parsing logs.
- **Deliverables.** `ActivitySource("Kassad")` with one activity per `EvaluateAsync` tagged `kassad.stage`, `kassad.outcome`, `kassad.model`, `kassad.had_error`; `Meter("Kassad")` with `kassad.verdicts` counter (tags: stage, policy_id, action, from_error) and `kassad.model.latency` histogram; no OTel package dependency (uses `System.Diagnostics` only); `Docs/specs/telemetry.md`.
- **Verification.** Test with `ActivityListener` and `MeterListener` asserts one activity and N verdict increments per evaluation; the sample, run with `dotnet-counters`, shows the meter.
- **Depends on.** 1.2.

##### 3.4 — Streaming evaluation design note

- **Goal.** Decide how streaming responses will be evaluated in a later version, without building it.
- **Deliverables.** `Docs/specs/streaming-evaluation.md` comparing: evaluate-on-complete (buffer, deliver late), chunked windows (evaluate every N tokens, ability to cut the stream), and post-hoc (stream through, evaluate after, flag retroactively); a recommendation with the latency/safety trade-off stated; open questions listed. `PROJECT_CONTEXT.md` open question updated to point at the note.
- **Verification.** The document exists, has a "Recommendation" section, and is linked from the README "Design notes".
- **Depends on.** 2.2.

### Phase 4 — Numbers published

**End state.** The eval harness runs from a single command, produces committed JSON, and the README table is generated from it.

**Success markers.** `kassad-eval report` regenerates the README section byte-identically from `eval/results/`; every threshold in the sample policy file has a measured precision/recall next to it.

##### 4.1 — Harness CLI and first dataset adapter

- **Goal.** Run one policy over one labeled dataset and emit per-row results.
- **Deliverables.** `Kassad.Eval` CLI (`System.CommandLine`, added to CPM) with `run --dataset <name> --policies <file> --out <path>`; `eval/datasets/deepset-prompt-injections.sh` download script + a C# adapter mapping rows to `(text, label)`; concurrency-limited runner with retry via `TypeSafeClient`; JSON output schema documented in `eval/README.md`.
- **Verification.** `kassad-eval run --dataset deepset --policies samples/.../kassad.policies.json --out eval/results/<date>-deepset.json` completes on the full set (or a stated sample) and the file contains one row per input with `probability`, `label`, `latency_ms`, `input_tokens`.
- **Depends on.** 1.2, 3.3 (latency measured consistently).

##### 4.2 — Metrics, calibration, and report

- **Goal.** Turn per-row results into the numbers the README promises.
- **Deliverables.** `report --in eval/results/ --format markdown`: per policy, precision/recall/F1 at each configured threshold plus a sweep; ROC AUC; 10-bin calibration table (predicted vs. observed); p50/p95 latency; cost per 1k checks from `input_tokens` × quoted rate (rate and its source printed in the table footer).
- **Verification.** Golden test: a hand-computed 20-row fixture produces the expected metrics to 3 decimals; the markdown renders on GitHub without layout breakage.
- **Depends on.** 4.1.

##### 4.3 — Second inbound dataset and a grounding set

- **Goal.** Meet the "≥ 2 inbound datasets" bar and seed the grounding stage.
- **Deliverables.** JailbreakBench adapter (behaviors + benign set); ToxicChat adapter if license allows, else documented reason; selection of a grounding dataset (candidates: a subset of a claim-verification set with source passages) recorded in `Docs/research/eval-datasets.md`; results JSON committed.
- **Verification.** `eval/results/` holds ≥ 3 dated files; `report` handles multiple datasets in one table.
- **Depends on.** 4.2, 3.1 (grounding helper).

##### 4.4 — README numbers table and threshold guidance

- **Goal.** Replace "Not yet measured" with generated numbers and honest guidance.
- **Deliverables.** `report --update-readme` writes between `<!-- numbers:start -->` / `<!-- numbers:end -->` markers; a CI job (`eval.yml`, scheduled weekly + on tag) that runs the harness on a fixed sample and fails if numbers drift beyond a stated tolerance; README paragraph explaining what the numbers do and don't mean; sample policy thresholds adjusted to the measured operating points, with the trade-off stated in comments.
- **Verification.** README shows the table; `git diff` after a second `report --update-readme` run is empty; `eval.yml` green.
- **Depends on.** 4.3, and every Phase 1–3 sub-phase (the measured thresholds must reflect the shipped engine).

##### 4.5 — `0.1.0` released

- **Goal.** Ship.
- **Deliverables.** `CHANGELOG.md` `0.1.0` section; `PROJECT_CONTEXT.md` status → "Released 0.1.0; maintenance + 0.2 planning", open questions pruned; `PublicAPI.Unshipped.txt` contents moved to `PublicAPI.Shipped.txt`; `git tag v0.1.0`.
- **Verification.** Every Definition of Done box is checked; nuget.org shows `0.1.0` for all four packages; the GitHub release notes list the changelog.
- **Depends on.** 4.4, 0.5.
