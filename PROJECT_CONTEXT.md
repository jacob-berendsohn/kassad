## Architectural decisions

- **2026-09-17** — .NET-first, four packages: `Kassad.Abstractions` (contracts, zero deps) / `Kassad` (engine) / `Kassad.TypeSafe` (client, depends only on Abstractions) / `Kassad.AspNetCore`. Same shape as `Microsoft.Extensions.*.Abstractions`. Reason: the client must be usable without the engine; no official .NET SDK exists for TypeSafe.
- **2026-09-17** — Abstractions are serialization-free. Wire mapping is hand-written in `Kassad.TypeSafe/SystemOneWire.cs`, not attribute-driven. Reason: out-of-order `type` discriminators break `[JsonPolymorphic]` on net8.0; hand mapping is robust to field order and extras.
- **2026-09-17** — Policies are JSON, not YAML. Loader is STJ with snake_case; `schemas/kassad-policies.schema.json` for editors. Reason: zero extra dependency, `IConfiguration`-friendly. YAML is a possible later add-on package, not core.
- **2026-09-17** — `on_error` (`fail_open` | `fail_closed`) is required per policy with no default. Validation rejects its absence. Do not add a default; the asymmetry between read paths and destructive paths is the point.
- **2026-09-17** — One policy = one question; all policies for a stage batch into one `DecisionRequest`. Thresholds live in policy config, never in `instructions`. Noul thresholds are probabilities; Score thresholds are level-index units; Choice uses per-option `actions`.
- **2026-09-17** — `VerdictAction` is ordered (`Allow < Flag < Review < Block`); a stage outcome is the max. Confidence below a floor (`min_confidence`) resolves to `Review`, never `Allow`.
- **2026-09-17** — Engine never throws for model failures; they become per-policy verdicts with `FromError = true`. Only `OperationCanceledException` from the caller's token propagates.
- **2026-09-17** — The engine's latency budget (`EvaluationOptions.Budget`, roadmap 1.2) is cooperative. `GuardrailEngine` links a `CancellationTokenSource` to the caller's token, calls `CancelAfter(budget)` and hands the model that single token; afterwards it tells the two apart: an `OperationCanceledException` while the caller's token is signaled propagates, and any exception while only the budget has fired (the model's own cancellation, or a `DecisionModelException` wrapping it) becomes per-policy error verdicts through `VerdictResolver.FromBudgetExceeded` (reason `budget exceeded (N ms); fail_closed → Block`), with `StageResult.BudgetExceeded = true` and therefore `HadModelError = true`. There is no `Task.WhenAny` race against the model task: a model that ignores its token is not cut off, and the doc on `Budget` says so (`TypeSafeClient` honors the token, including during retry backoff). Reason: a race would leave an orphaned in-flight request whose faults and disposed token nobody owns, for implementations the `IDecisionModel` contract already forbids. `EvaluationOptions` goes through the options pattern like `TypeSafeClientOptions` and `KassadOptions`, so `Kassad` now references `Microsoft.Extensions.Options` (already pinned per TFM); `AddKassad` validates `Budget` (positive, or `null` for none) with `ValidateOnStart`, and the constructor re-checks it for direct construction. `GuardrailEngine` keeps one constructor, `(model, policies, IOptions<EvaluationOptions>? = null, ILogger? = null)`: a second overload with optional parameters would trip RS0026 and make `Microsoft.Extensions.DependencyInjection` constructor selection ambiguous.
- **2026-09-17** — `TypeSafeClient` is a singleton that pulls an `HttpClient` from `IHttpClientFactory` per call. Reason: typed-client-as-singleton captures one handler forever and breaks DNS/handler rotation.
- **2026-09-17** — `TypeSafeClient` maps HTTP 400 and 422 both to `TypeSafeRequestException` and retries neither. Reason: the live API returns 422 for schema violations (pydantic-style `detail` array whose `loc` names the field) and 400 for semantic ones (unknown model, a question with neither instructions nor criteria); both mean the request must change. Wire fixtures under `tests/Kassad.TypeSafe.Tests/Fixtures/` are recorded from the live API by the `FixtureRecorder` test helper (opt-in via `KASSAD_RECORD_FIXTURES=1`) and never hand-edited; `SystemOneWireTests` read expected values from the files, so re-recording needs no test changes.
- **2026-09-17** — Rejection responses omit policy ids unless `IncludePolicyIdsInResponse = true`. Reason: naming the check that fired is reconnaissance for an attacker. Verdicts are always fully logged.
- **2026-09-17** — Apache-2.0. Reason: patent grant matters to enterprise adopters more than MIT's brevity.
- **2026-09-17** — Versioning by MinVer from `v*` tags; releases via NuGet Trusted Publishing. No version numbers or API keys are ever committed.
- **2026-09-17** — Release mechanics, proven by `v0.1.0-preview.1`: one nuget.org Trusted Publishing policy scoped to owner `jacob-berendsohn`, repo `kassad`, workflow file `release.yml` and GitHub environment `nuget`, with `NUGET_USER` stored as an environment secret. nuget.org matches the token's repository, the workflow file name and the environment claim and ignores the git ref, so the `push` of a `v*` tag is what publishes. Tags go on a commit that is already on `main` and are pushed one at a time by name, never with `git push --tags`. Reason: one policy, one workflow and one environment keep the OIDC trust surface minimal; a tag on `main` keeps MinVer's height and the generated release notes coherent. Because the repo is private, nuget.org created the policy in its temporary 7-day state; this first publish made it permanent.
- **2026-09-17** — The repo ships its own `nuget.config`: `<clear />` plus nuget.org as the only source. Reason: Central Package Management raises NU1507 whenever a machine has more than one feed configured, and warnings are errors; a public library also should not restore from private feeds. Adding a feed requires `packageSourceMapping`.
- **2026-09-17** — Every project generates an XML documentation file, including tests, samples and eval (with `CS1591` suppressed outside `src/`). Reason: IDE0005 (unnecessary usings) only runs in build when `GenerateDocumentationFile` is true, and we want that check everywhere. `dotnet_style_require_accessibility_modifiers` is `for_non_interface_members`, the dotnet-repo convention.
- **2026-09-17** — Repo/project named after Fedmahn Kassad (Hyperion Cantos). Package prefix `Kassad.*`. Do not use `TypeSafe.*` as a prefix anywhere; it's the vendor's.
- **2026-09-17** — The public surface of the four `src/` packages is locked by `Microsoft.CodeAnalysis.PublicApiAnalyzers`: every public symbol is listed in the project's `PublicAPI.Unshipped.txt` and RS0016/RS0017 are errors, so a public change that does not edit the API file fails the build. Regenerate entries per project with `dotnet format analyzers src/<Project>/<Project>.csproj --diagnostics RS0016` (a solution-level run populated only the first project) and review the diff. `PublicAPI.Shipped.txt` stays empty until a release moves the Unshipped entries into it. `AnalysisLevel` is `latest-recommended`; the only suppressions it needed are test-only (`CA1711` for xunit `*Collection` classes, `CA1861` for array literals in assertions), scoped in `.editorconfig` under `[tests/**.cs]` with a reason each. `src/` gained no suppressions.
- **2026-09-17** — The code-only stages take typed states (roadmap 3.1): `ToolCallState(UserIntent, ToolName, ToolSchemaJson, ArgumentsJson)` and `GroundingState(Claim, SourcePassage, SourceId?)` in `Kassad.Abstractions`. The records are plain data, in keeping with the serialization-free abstractions; the field names the model sees (`user_intent`, `tool_name`, `tool_schema`, `arguments`; `claim`, `source_passage`, `source_id`) are documented on the records and written by hand in `SystemOneWire.WriteState`, next to the question mapping, so every `IDecisionModel` implementation owns its own rendering of them. `Kassad.TypeSafe` embeds `ToolSchemaJson` and `ArgumentsJson` as JSON values, falls back to a string when the text does not parse (an LLM's malformed arguments still reach the policies), and leaves `source_id` out when null. `GuardrailEngineExtensions.EvaluateToolCallAsync` / `EvaluateGroundingAsync` live in `Kassad.Engine` and forward the record as the state, so a direct `EvaluateAsync(Stage.ToolCall, record)` produces the same wire shape; there is no flat-argument overload because a second overload with an optional `CancellationToken` trips RS0026. Reason: converting to a `JsonNode` in the engine would have given the helpers and the direct call different shapes, and exposing System.Text.Json types from Abstractions would have broken "contracts only". `tests/Kassad.TypeSafe.Tests` now references `Kassad` so `GuardrailEngineLiveTests` can run policies through the engine against the real client; package dependencies are unchanged.
- **2026-09-17** — `Kassad.AspNetCore.Tests` (roadmap 2.1) hosts the middleware through `WebApplicationFactory` without an application entry point. `KassadWebApplicationFactory` overrides `CreateHostBuilder` to start from an empty `HostBuilder`, and in `ConfigureWebHost` registers the `FakeDecisionModel`, `AddKassad` and `AddKassadAspNetCore`, builds the pipeline (a probe that records the trace id, `UseKassadInbound`, an echo endpoint that records `GetKassadInboundResult()` and the body it read) and sets the content root to the test output directory: with no content-root manifest entry for the test assembly, the base class falls back to a directory named after it next to the solution file, which does not exist (the fallback itself needs a `.sln` or `.slnx` up the tree; both pinned `Microsoft.AspNetCore.TestHost` versions accept `.slnx`, verified in the 8.0.31 binary). Reason: the sample cannot be the entry point (net10.0 only, needs `TYPESAFE_API_KEY`), and a dedicated host project would be a third moving part for a pipeline that is three lines of registration. `FakeDecisionModel` and `TestPolicies` are shared with `Kassad.Tests` as linked `Compile` items rather than through a project reference, because a test assembly that references another drags its generated entry point and runner along. Roadmap 2.2 reuses the project and the factory.
- **2026-09-17** — `Kassad.AspNetCore.Tests` drives `KassadDelegatingHandler` through the real client wiring (roadmap 2.2), not through a bare `HttpMessageInvoker`. `KassadHandlerHarness` builds a `ServiceCollection` with `AddKassad`, `AddKassadAspNetCore` and `AddHttpClient(...).ConfigurePrimaryHttpMessageHandler(stub).AddKassadHandler()`, and every test sends through a client from `IHttpClientFactory`, so the transient handler registration and `KassadOptions` validation run where an application meets them (invalid options surface as `OptionsValidationException` from the first `CreateClient()`). The `StubProvider` at the end of the chain records the request bytes it received and answers with scripted responses; a forward-only stream with a read counter proves that a `text/event-stream` response goes back to the caller unbuffered (sent with `HttpCompletionOption.ResponseHeadersRead`, as an SSE consumer would). The streaming warning is asserted with `FakeLogger<KassadDelegatingHandler>` from `Microsoft.Extensions.Diagnostics.Testing`, registered as the handler's `ILogger<T>` so its collector sees only the handler's lines; the package is pinned per TFM like `Mvc.Testing` (`8.10.0` / `10.10.0`, the latest of each line), because its 10.x line would drag the net8.0 test build past its `Microsoft.Extensions.*` 8.0.x floors. Reason: the roadmap names `FakeLogger`, it is Microsoft's own `ILogger` test double, and a hand-rolled one would be thirty more lines of test code to maintain; if the dependency is unwanted, `FakeLogger<T>` is replaced by a small `ILogger<T>` that lists its records and nothing else changes. The handler needs no web host, so the `WebApplicationFactory` from 2.1 is not involved; the two fixtures share only the linked `FakeDecisionModel` and `TestPolicies`.

- **Known bug: rejection content type. Resolved 2026-09-17.** `KassadInboundMiddleware.WriteRejectionAsync` set `application/problem+json` and then called the two-argument `WriteAsJsonAsync`, which reset the header to `application/json; charset=utf-8`; confirmed live in roadmap 1.3 (the sample's 403 was plain JSON). Fixed in roadmap 2.1 by handing the type to the overload that takes one (`WriteAsJsonAsync(problem, options: null, contentType: "application/problem+json", ...)`): the header is now exactly `application/problem+json`, no charset parameter, as the spec's examples show (JSON is UTF-8 by definition). The 403 and 413 integration tests in `Kassad.AspNetCore.Tests` assert it; the 2026-09-17 recording in `samples/README.md` predates the fix and says so.
- **Known bug: loader crash on a malformed `actions` entry. Resolved 2026-09-17.** `PolicyDocument.Parse` recorded the validation error for an entry whose `action` was missing or `null`, then dereferenced it anyway, so callers saw `InvalidOperationException`/`NullReferenceException` instead of `PolicyValidationException`. Fixed in roadmap 1.1: `Parse` skips policy construction for any entry that added an error. The rule-for-rule tests found three more crash paths of the same class in the same function, fixed in the same sub-phase: a `null` entry in `policies` (`NullReferenceException`), a non-string `true`/`false` value in noul `criteria` and a non-string level in score `criteria` (both `InvalidOperationException` from `JsonElement.GetString()`). Two silent coercions beside them were tightened to errors because the spec and schema already forbade the input: a non-string choice description read as `null`, and a `null` score level read as an empty string.
- **Loader leniencies the spec does not state.** Open. Found by the 1.1 reconciliation and left as they are because none contradicts a stated rule: enum-valued fields (`stage`, `type`, `on_error`, `action`) match case-insensitively, so `"type": "NOUL"` loads; the reader accepts integer enum values (`"stage": 0` is `inbound`), and while `stage` and `on_error` are range-checked in the second pass, `action` is not, so `"action": 9` yields a `ChoiceRule` with an undefined `VerdictAction`; unknown properties are ignored at every level (root, policy, `thresholds`, `actions[*]`) although the schema sets `additionalProperties: false`; the `id` snake_case pattern is schema-only. Default assumption: stay lenient through `0.1.0` and revisit with a spec change if a user hits one. The strict version is `allowIntegerValues: false` on the enum converter, `UnmappedMemberHandling = Disallow` on the serializer options, and an `Enum.IsDefined` check on `ChoiceRule.Action` in `PolicySet.Validate`, each one line plus a `Theory` row.
- **Inbound state extraction.** The middleware and handler evaluate the raw body as the state. Open. Default assumption: keep raw-body until roadmap 2.3 introduces `IStateExtractor` (OpenAI `messages[]`, Anthropic `messages[]`, plain text).
- **Streaming responses.** Passed through unevaluated with a warning. Open. Default assumption: no buffering of SSE; token-level evaluation is roadmap 3.4, design TBD. Verified by the 2.2 handler tests: the provider's response object goes back to the caller with zero bytes read from its stream, no `Kassad-Outcome` header, the inbound stage still evaluated, and exactly one Warning (`Kassad outbound: streaming response from <uri> passed through unevaluated`).
- **Oversized body with `fail_open` in the DelegatingHandler** throws because content is already consumed. Open. Default assumption: `fail_closed` is the recommended setting; pass-through is roadmap 3.2. Pinned by two 2.2 tests (`InvalidOperationException` naming roadmap 3.2, for an oversized request with the provider never called and for an oversized response with the provider called once); 3.2 replaces those tests together with the behavior. The `fail_closed` path is covered for both directions, with and without a declared `Content-Length`.
- **Handler response fidelity.** Open. Three things the 2.2 tests observed and left as they are, because none contradicts `Docs/specs/rejection-response.md`: (a) on an allowed response the `Kassad-Outcome` header carries the outbound stage's outcome only, so an inbound `Review` that passed is invisible to the caller (the middleware exposes its result through `HttpContext.Items`; the handler has no equivalent), pinned by `Outcome_header_reports_the_outbound_stage_when_inbound_was_review`; (b) the handler's synthesized rejections carry no `Kassad-Outcome` header while the middleware's carry `Kassad-Outcome: block`, each as the spec's example for it shows; (c) an allowed response is re-materialized as a `StringContent` with only `Content-Type` copied from the original, so any other entity header the provider sent (`Content-Language`, `Content-Encoding`, `Expires`, ...) is dropped, and the synthesized rejection's `Content-Type` is `application/json; charset=utf-8` where the spec example shows the bare type. Default assumption: leave all of it through 2.3 and 2.4, decide there whether the header should report the more severe of the two stages or split into one header per stage, and copy every content header when 3.2 reworks the read path.

- **`dotnet format analyzers --diagnostics RS0016` applies no fix. Resolved 2026-09-17.** Found in roadmap 3.1 on SDK 10.0.202: the run applied nothing (`Formatted 0 of 16 files`) because the workspace loaded `PublicAPI.Shipped.txt` and `PublicAPI.Unshipped.txt` twice (`Duplicate source file` at diagnostic verbosity): `Microsoft.CodeAnalysis.PublicApiAnalyzers` 5.6.0 adds both as `AdditionalFiles` through its own build targets whenever they exist next to the project, and `src/Directory.Build.props` added them again with two explicit items. Fixed by deleting the two items; the comment above them now says the package registers the files itself, and nothing else changed (the `CONTRIBUTING.md` instruction stays as it is). Verified on `main`: `dotnet build -c Release --no-incremental` is 0 warnings / 0 errors for the solution; with `Kassad.ChoiceAnswer.Confidence.get -> double` deleted from `src/Kassad.Abstractions/PublicAPI.Unshipped.txt` the project build fails with RS0016 on net8.0 and net10.0 and nothing else, and the CONTRIBUTING command restores the entry (`Formatted 2 of 14 files` on `main`, 16 on the 3.1 branch because its `States.cs` counts once per TFM; no duplicate-file warning). One behavior of the analyzer's code fix to know about: when the reported symbol belongs to a `record`, the same run also deletes that record's compiler-synthesized members from the file as stale siblings (`Deconstruct`, the three `Equals`, `GetHashCode`, `ToString`, `<Clone>$`, `operator ==`/`!=`: nine lines for `ChoiceAnswer`), the next build reports exactly those with RS0016, and a second run adds them back, after which the file is byte-identical to the committed one. For a non-record type (an enum member was tried) one run restores the file byte for byte. So: run the command, build, run it again if the build still fails with RS0016 on a record's synthesized members, then review the diff as before. Before the fix, the 3.1 entries had been taken verbatim from the build's `RS0016: Symbol '...'` messages and inserted in the fixer's order (case-insensitive, then ordinal).

## Repository layout

```
/src/Kassad.Abstractions/   contracts only — no dependencies, no serialization attributes
/src/Kassad/                engine; Policies/ (model + JSON loader + validation), Engine/ (resolver, engine)
/src/Kassad.TypeSafe/       HTTP client; SystemOneWire.cs is the only place that knows the JSON shape
/src/Kassad.AspNetCore/     middleware + DelegatingHandler + DI extensions
/tests/                     xunit; Kassad.TypeSafe.Tests/Fixtures/ holds recorded wire JSON; Kassad.AspNetCore.Tests hosts the middleware in a TestServer (roadmap 2.1) and drives the handler through IHttpClientFactory over a stub provider (roadmap 2.2)
/samples/Kassad.Sample.ChatApi/  runnable minimal API; kassad.policies.json is the reference policy file
/samples/README.md               expected responses and log lines from the sample against the live API (roadmap 1.3)
/eval/                      harness (stub) + datasets/ scripts + results/ (committed JSON); data/ is git-ignored
/schemas/                   JSON Schema for policy files, referenced by $schema in policy documents
/Docs/                      see Docs/README.md
```

`src/`, `tests/`, `samples/`, `eval/` each have a `Directory.Build.props` that imports the root one. Package metadata and analyzers are configured there, not per-csproj. The root `nuget.config` pins nuget.org as the only package source.

## Environment / secrets

- `TYPESAFE_API_KEY` — bearer token for api.typesafe.ai. Read by `TypeSafeClientOptions` when `ApiKey` is unset. Required by the sample and by live tests; absent in unit tests by design.
- `KASSAD_RECORD_FIXTURES` — set to `1` (together with `TYPESAFE_API_KEY`) to let the `FixtureRecorder` test in `tests/Kassad.TypeSafe.Tests` overwrite `Fixtures/*.json` from the live API. Never set in CI; the `live` job reports the recorder as skipped.
- `NUGET_USER` — GitHub Actions secret on the `nuget` environment: nuget.org profile name used by `NuGet/login@v1` for Trusted Publishing. Not an API key, not an email.
- `TYPESAFE_API_KEY` (Actions secret) — enables the `live` CI job on pushes to the owner's repo only.
