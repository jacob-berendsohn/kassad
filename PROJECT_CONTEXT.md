## Architectural decisions

- **2026-09-17** — .NET-first, four packages: `Kassad.Abstractions` (contracts, zero deps) / `Kassad` (engine) / `Kassad.TypeSafe` (client, depends only on Abstractions) / `Kassad.AspNetCore`. Same shape as `Microsoft.Extensions.*.Abstractions`. Reason: the client must be usable without the engine; no official .NET SDK exists for TypeSafe.
- **2026-09-17** — Abstractions are serialization-free. Wire mapping is hand-written in `Kassad.TypeSafe/SystemOneWire.cs`, not attribute-driven. Reason: out-of-order `type` discriminators break `[JsonPolymorphic]` on net8.0; hand mapping is robust to field order and extras.
- **2026-09-17** — Policies are JSON, not YAML. Loader is STJ with snake_case; `schemas/kassad-policies.schema.json` for editors. Reason: zero extra dependency, `IConfiguration`-friendly. YAML is a possible later add-on package, not core.
- **2026-09-17** — `on_error` (`fail_open` | `fail_closed`) is required per policy with no default. Validation rejects its absence. Do not add a default; the asymmetry between read paths and destructive paths is the point.
- **2026-09-17** — One policy = one question; all policies for a stage batch into one `DecisionRequest`. Thresholds live in policy config, never in `instructions`. Noul thresholds are probabilities; Score thresholds are level-index units; Choice uses per-option `actions`.
- **2026-09-17** — `VerdictAction` is ordered (`Allow < Flag < Review < Block`); a stage outcome is the max. Confidence below a floor (`min_confidence`) resolves to `Review`, never `Allow`.
- **2026-09-17** — Engine never throws for model failures; they become per-policy verdicts with `FromError = true`. Only `OperationCanceledException` from the caller's token propagates.
- **2026-09-17** — The engine's latency budget (`EvaluationOptions.Budget`, roadmap 1.2) is cooperative. `GuardrailEngine` links a `CancellationTokenSource` to the caller's token, calls `CancelAfter(budget)` and hands the model that single token; afterwards it tells the two apart: an `OperationCanceledException` while the caller's token is signaled propagates, and any exception while only the budget has fired (the model's own cancellation, or a `DecisionModelException` wrapping it) becomes per-policy error verdicts through `VerdictResolver.FromBudgetExceeded` (reason `budget exceeded (N ms); fail_closed → Block`), with `StageResult.BudgetExceeded = true` and therefore `HadModelError = true`. There is no `Task.WhenAny` race against the model task: a model that ignores its token is not cut off, and the doc on `Budget` says so (`TypeSafeClient` honors the token, including during retry backoff). Reason: a race would leave an orphaned in-flight request whose faults and disposed token nobody owns, for implementations the `IDecisionModel` contract already forbids. `EvaluationOptions` goes through the options pattern like `TypeSafeClientOptions` and `KassadOptions`, so `Kassad` now references `Microsoft.Extensions.Options` (already pinned per TFM); `AddKassad` validates `Budget` (positive, or `null` for none) with `ValidateOnStart`, and the constructor re-checks it for direct construction. `GuardrailEngine` keeps one constructor, `(model, policies, IOptions<EvaluationOptions>? = null, ILogger? = null)`: a second overload with optional parameters would trip RS0026 and make `Microsoft.Extensions.DependencyInjection` constructor selection ambiguous.
- **2026-09-17** — `TypeSafeClient` is a singleton that pulls an `HttpClient` from `IHttpClientFactory` per call. Reason: typed-client-as-singleton captures one handler forever and breaks DNS/handler rotation.
- **2026-09-17** — `TypeSafeClient` maps HTTP 400 and 422 both to `TypeSafeRequestException` and retries neither. Reason: the live API returns 422 for schema violations (pydantic-style `detail` array whose `loc` names the field) and 400 for semantic ones (unknown model, a question with neither instructions nor criteria); both mean the request must change. Wire fixtures under `tests/Kassad.TypeSafe.Tests/Fixtures/` are recorded from the live API by the `FixtureRecorder` test helper (opt-in via `KASSAD_RECORD_FIXTURES=1`) and never hand-edited; `SystemOneWireTests` read expected values from the files, so re-recording needs no test changes.
- **2026-09-17** — Rejection responses omit policy ids unless `IncludePolicyIdsInResponse = true`. Reason: naming the check that fired is reconnaissance for an attacker. Verdicts are always fully logged.
- **2026-09-17** — Apache-2.0. Reason: patent grant matters to enterprise adopters more than MIT's brevity.
- **2026-09-17** — Versioning by MinVer from `v*` tags; releases via NuGet Trusted Publishing. No version numbers or API keys are ever committed.
- **2026-09-17** — Release mechanics, proven by `v0.1.0-preview.1`: one nuget.org Trusted Publishing policy scoped to owner `jacob-berendsohn`, repo `kassad`, workflow file `release.yml` and GitHub environment `nuget`, with `NUGET_USER` stored as an environment secret. nuget.org matches the token's repository, the workflow file name and the environment claim and ignores the git ref, so the `push` of a `v*` tag is what publishes. Tags go on a commit that is already on `main` and are pushed one at a time by name, never with `git push --tags`. Reason: one policy, one workflow and one environment keep the OIDC trust surface minimal; a tag on `main` keeps MinVer's height and the generated release notes coherent. Because the repo is private, nuget.org created the policy in its temporary 7-day state; this first publish made it permanent.

Reason: Central Package Management raises NU1507 whenever a machine has more than one feed configured, and warnings are errors; a public library also should not restore from private feeds. Adding a feed requires `packageSourceMapping`.

Reason: IDE0005 (unnecessary usings) only runs in build when `GenerateDocumentationFile` is true, and we want that check everywhere. `dotnet_style_require_accessibility_modifiers` is `for_non_interface_members`, the dotnet-repo convention.

- **2026-09-17** — Telemetry (roadmap 3.3) goes through `System.Diagnostics` only: a static `ActivitySource("Kassad")` and a static `Meter("Kassad")` in `KassadTelemetry`, no OpenTelemetry package and no `IMeterFactory`, so the `GuardrailEngine` constructor is unchanged and `AddMeter("Kassad")` / `--counters Kassad` see one meter per process. `EvaluateAsync` is one `Kassad.Evaluate` activity (`ActivityKind.Internal`; tags `kassad.stage` and `kassad.model` at start, `kassad.outcome` and `kassad.had_error` on completion; status `Unset` even when the model failed, because verdicts were produced, and `Error` with `cancelled by the caller` when the caller's token propagated), one `kassad.verdicts` increment per verdict (`kassad.stage`, `kassad.policy_id`, `kassad.action`, `kassad.from_error`) and one `kassad.model.latency` sample per model call (`kassad.stage`, `kassad.model`, `kassad.had_error`; unit `ms`, because the OpenTelemetry SDK's default explicit buckets are millisecond-shaped and `InstrumentAdvice` is .NET 9+ only, so a net8.0 consumer gets a usable distribution without a view). Tag names carry the `kassad.` prefix on the metrics too (the roadmap's `stage, policy_id, …` read as shorthand), values use the policy-file and `Kassad-Outcome` spellings, no user content is ever a tag, and measurements are recorded before the activity stops so exemplars can link to it. A stage with no policies still gets its activity (`allow`) but no measurements. The five names are public constants on `KassadTelemetry`; the source, meter, instruments and tag names are internal. Reason: the roadmap asks for `System.Diagnostics` only, and a static source and meter are what a .NET library without a DI-created meter does; the tests attribute through a per-test parent activity instead of a meter instance. `Docs/specs/telemetry.md` is the contract.
- **2026-09-17** — The handler's body read is bounded (roadmap 3.2): `KassadDelegatingHandler.ReadBoundedAsync` reads a text body through `HttpContent.ReadAsStreamAsync` up to `MaxBodyBytes` plus one byte, and a body whose declared `Content-Length` is already over the limit is not read at all. Reading through the content's stream moves the stream a `StreamContent` or a response straight off the wire would send from (a `ByteArrayContent` hands out a separate `MemoryStream`, but the handler cannot tell which kind it holds), so every body that was read is re-attached before it travels on: one that fits as `BufferedContent`, a `ByteArrayContent` over the bytes read; one that overflowed under `fail_open` as `ResumedContent`, an `HttpContent` that serializes the bytes read and then the rest of the original stream (`PrefixedStream`) and, like the runtime's own response content, can be sent or read once and throws on a second attempt rather than sending a truncated body. Both copy every original content header verbatim (`HttpHeaders.NonValidated` into `TryAddWithoutValidation`, `Content-Length` and `Content-Type` included; `ResumedContent` computes no length of its own, so an undeclared body stays undeclared) and dispose the original content with themselves, because `HttpClient` does not dispose request content and the caller's `response.Dispose()` has to reach the provider's stream. A body oversized by declaration stays the content it was. Consequences: an allowed response comes back from the exact bytes read under all of its headers (item (c) of the 2.2 fidelity caveat); a `fail_open` pass-through streams to a `ResponseHeadersRead` caller with nothing buffered beyond the limit; `OutboundState.Request` is `null` for a request that was passed through unevaluated, as for a non-text one; anything past `int.MaxValue - 1` bytes counts as oversized however high `MaxBodyBytes` is set, because a body has to fit in one array to be evaluated. Reason: the roadmap asks for a read that stops at `MaxBodyBytes + 1` without consuming the rest and re-attaches prefix plus remainder; `LoadIntoBufferAsync(maxBufferSize)`, the framework's own bound, throws when exceeded and leaves the content unusable.
- **2026-09-17** — The HTTP components evaluate extracted states, not raw bodies (roadmap 2.3). `IStateExtractor { object? Extract(string body, string? contentType, Stage stage) }` lives in `Kassad.AspNetCore`; `KassadOptions.StateExtractor` holds the one instance the middleware and the handler share (validated non-null at startup), called once per textual body after the size check with `Inbound` for a request body and `Outbound` for a response body. `DefaultStateExtractor` selects by content type (media types containing `json`, or none, are parsed; `text/plain` never is) and shape: a JSON object with a `messages` array is a chat request, read by `AnthropicMessagesExtractor` when it has a top-level `system` field and by `OpenAIChatCompletionsExtractor` otherwise into an `InboundState(UserMessage, SystemPrompt)`, the text of the last `user` message (string content as-is; the `text` parts or blocks of an array joined with newlines; images, audio, tool calls and tool results dropped) and the system prompt from wherever that provider puts it (`system` and `developer` messages joined with blank lines, or the top-level `system` string or text blocks); a response with `choices[]` or `"type": "message"` is read into the reply string. Each provider class reads only its own provider's locations, so the sniff is one rule and a body with no system prompt reads the same either way. `null` from an extractor means "not recognised" and the caller evaluates the whole body, which `RawBodyExtractor` also does explicitly; a chat request whose last user turn has no text and a response with no reply text (a tool call) fall back the same way, so nothing is ever skipped, and the built-ins never throw (malformed JSON and nesting past the reader limit are whole bodies too). `KassadDelegatingHandler.OutboundState` was extended, not replaced: `Request` and `Response` remain the whole bodies but are `null` when the new `UserMessage`, `SystemPrompt` and `Completion` carry that body, so each body appears once and the wire is `{ user_message, system_prompt, completion }` for recognised traffic and `{ request, response }` otherwise, nulls omitted; the handler folds an `InboundState` and a reply string from any extractor, a string returned for a request is used as the request text, and any other custom object is evaluated as returned on the inbound stage but not folded. Both records carry `[JsonPropertyName]` and `[JsonIgnore(WhenWritingNull)]` attributes and take `SystemOneWire`'s default System.Text.Json path, since `Kassad.TypeSafe` does not reference `Kassad.AspNetCore`; the names are the contract in `Docs/specs/state-extraction.md`, and `StateExtractionWireTests` pins the bytes. Reason: the roadmap fixes the interface and asks for the last user turn and the system prompt as separate fields; a record with attributes in the integration package keeps Abstractions serialization-free while every STJ-based model renders the same names; dropping the whole body once a shape is recognised, instead of sending both, saves two to three times the tokens (base64 images in prompts most of all) while the fallback keeps every unrecognised shape fully visible. Consequence recorded as a caveat below: tool results and earlier turns are no longer seen by inbound policies. Rejected: a `JsonObject` state (no typed access, nothing to fold into `OutboundState`); `object?`-typed `Prompt` / `Completion` fields on `OutboundState` (generic, but `request.user_message` nesting and a duplicated raw body); one shared request walk for both providers (each class would then read the other's system-prompt location too). The sample sets `StateExtractor` to a `ChatRequestStateExtractor` that maps its `{"message"}` body to an `InboundState` and delegates everything else to the default, so its inbound policies see `user_message` too. `tests/Kassad.TypeSafe.Tests` now also references `Kassad.AspNetCore` and links `ProviderBodies.cs` from `Kassad.AspNetCore.Tests` for the wire-shape and live tests; package dependencies are unchanged.
- **2026-09-18** — The sample reaches a real provider through its own Kassad-wrapped `HttpClient`, selected by configuration (roadmap 2.4). `Llm:Provider` is `echo` (default: the endpoint answers itself and only the middleware runs) or `openai`: `OpenAIChatProvider` in `Program.cs` posts `{ model, messages: [system, user] }` to `v1/chat/completions` on the `llm` client with `System.Net.Http.Json` and reads `choices[0].message.content` back through `JsonDocument`, so the handler sees the exact bytes an application would send and no OpenAI SDK is involved (none is pinned in `Directory.Packages.props`, and the out-of-scope list forbids OpenAI as anything but the guarded provider). `OPENAI_API_KEY` is read once at startup and the app refuses to start without it when `openai` is selected, the fail-fast `AddKassad` applies to a bad policy file; `Llm:Model` defaults to `gpt-4o-mini`; `Llm:BaseAddress` keeps its `https://api.openai.com/` default so the client can be pointed at any chat-completions endpoint. The endpoint reads the handler's verdict from the `Kassad-Outcome` header of the provider's response and reports it as `kassad.outbound.outcome` beside the middleware's `kassad.inbound` result (the former top-level `kassad` fields) and a `provider` name; a failed call is told apart by its body: an `error.type` starting with `kassad_` is the handler's own rejection per `Docs/specs/rejection-response.md` and goes to the caller as it is (a blocked completion is a 403 `kassad_blocked`), anything else is the provider's error and becomes a 502 with the provider's status and body inside, because a 401 for the server's key is not the caller's fault. Consequences: an allowed request in `openai` mode costs three decision-model calls (the middleware evaluates `{ user_message }`, the handler `{ user_message, system_prompt }` for the outgoing body and `{ user_message, system_prompt, completion }` for the reply), and a `/chat` response always carries the middleware's inbound outcome in `Kassad-Outcome`, so a 403 whose body says `Outbound rejected by policy` arrives under `Kassad-Outcome: allow`; the fidelity caveat records the decision to leave that as it is. Rejected: falling back to `echo` when the key is missing (hides a misconfiguration), passing provider errors through with their own status (a 401 to the end user for the server's key), synthesizing a problem+json for a blocked completion (the handler's body is the documented contract). Verified end to end against a local stand-in for chat completions with every verdict from the live TypeSafe API, not against api.openai.com (no key was available to the session; caveat below).
- **2026-09-18** — Streaming responses (roadmap 3.4, design only; nothing lands before `0.1.0`): a later version evaluates a `text/event-stream` response as chunked windows over the accumulated prefix, forwarding frames as they arrive (trailing delivery), taking a checkpoint when at least `N` characters have arrived and no checkpoint is in flight, always taking a gated checkpoint at the frame that ends the text, and cutting the stream when a checkpoint's outcome reaches `RejectAt` by emitting the provider's own stop vocabulary (`finish_reason: "content_filter"` for OpenAI, `stop_reason: "refusal"` for Anthropic) and disposing the provider's response. Evaluate-on-complete and post-hoc are settings of the same mechanism (gated delivery with one checkpoint at the end; trailing delivery with no mid-stream checkpoints). Proposed defaults when it lands: `Windowed`, trailing, terminal checkpoint only until the eval harness has measured prefix calibration and the exposure/request curve; `Buffer` and gated delivery available from the first release; an `on_partial` policy field required of `outbound` policies once an interval is configured; a mid-stream checkpoint without a verdict is no news and `on_error` resolves at the terminal checkpoint; the verdict reaches SDK-based applications through a callback, since they see neither headers nor trailers. Reason: trailing delivery keeps TTFT and throughput as the caller intended and bounds exposure to about `max(N, r·t) + r·t` characters (a sentence or two at illustrative rates) without guaranteeing zero, which gated delivery and buffering do at the cost of a delayed, bursty or non-streaming response; against a front-loaded payload the inbound stage is the first line and gated delivery is one option away. Rejected as the default: buffering (an application that meant to stream turns Kassad off before accepting an eight-second first token) and pass-through once the mechanism exists (a guardrail that skips streams it can judge). `Docs/specs/streaming-evaluation.md` has the comparison, the arithmetic and 17 open questions with a default assumption each; names there are proposals, not contracts.
- **2026-09-18** — Tests bound wall-clock time by magnitude, never as a latency measurement, and race a timer only against a fake that cannot finish on its own. `Budget_overrun_becomes_error_verdicts_without_waiting_for_the_model` (roadmap 1.2) asserted that a 50 ms budget came back within 100 ms against a fake answering at 500 ms. That bound failed CI three times: 141 ms and 545 ms in the parallel phase, then 945 ms on 2026-09-18 (ubuntu-latest/net8.0, PR #28's first run, 35404284020) inside its own `DisableParallelization` collection and after a warm-up, while every passing CI run finished the whole test in 58–83 ms. xunit's `XunitTestAssemblyRunner` awaits every parallel collection before it starts the non-parallel ones, and the trx files agree once their times are read as what they are, the stamps xunit's reporter thread puts on each message as it dispatches it, which trail a burst of fast results by tens of ms: none of the ten CI runs examined (both TFMs of run 35404284020's ubuntu and windows legs, of the passing rerun 35404467841 and of PR #29's own run 35406565348) stamps another result of the process after this test's measured call began except inside the reporter's backlog, where PR #29's ubuntu leg stamps 37 sub-millisecond theory results in the 58 ms the reporter was behind when the net8.0 test started (3 more in the 4 ms backlog of its net10.0 run), all before the test's own start stamp, while the failing run's stamps run 94 ms ahead of the call with none inside its 945 ms. So xunit's isolation works and the process was idle apart from this call; what stalled it was the runner: `dotnet test` at solution level runs the other test projects and the other target framework concurrently, and the failing call overlapped the `Kassad.AspNetCore.Tests` net8.0 coverage report and the `Kassad.Tests` net10.0 start-up (coverlet instrumenting the `src` assemblies, test-host launch, discovery) on a 4-vCPU machine. The 923 ms measured exceeded the fake's own 500 ms delay, so the process as a whole was descheduled, timers included: the `CancelAfter` timer was not late on its own, coverage instrumentation of the measured path had already been paid by the warm-up, and thread-pool start-up cannot apply to a test that runs last. Rule, applied to that test: the fake waits a minute so only the budget's cancellation can end the call (the 3.3 / PR #23 pattern); `BudgetExceeded`, the null `Usage` and the cancelled token carry the proof that the engine did not wait for the model (had it waited, the fake would have answered and `BudgetExceeded` would be false); the one remaining wall-clock bound is 5 s, two orders of magnitude above the budget, five times the worst stall CI has shown and twelve times under the model's delay, so it still catches a budget that fires seconds late while a budget that never fires fails a minute later on `BudgetExceeded`. A tight bound is not bought back by serializing CI (`-p:TestTfmsInParallel=false` or `-m:1` would slow the `build` job to protect one number the runner still could not guarantee), and the warm-up went with the bound it protected: a cold single run now measures 81–105 ms (254–278 ms for the first run after a build) because the budget path is JIT-compiled inside the measured call, the full-suite run 53–62 ms, both noise against 5 s.

- **Loader leniencies the spec does not state.** Open. Found by the 1.1 reconciliation and left as they are because none contradicts a stated rule: enum-valued fields (`stage`, `type`, `on_error`, `action`) match case-insensitively, so `"type": "NOUL"` loads; the reader accepts integer enum values (`"stage": 0` is `inbound`), and while `stage` and `on_error` are range-checked in the second pass, `action` is not, so `"action": 9` yields a `ChoiceRule` with an undefined `VerdictAction`; unknown properties are ignored at every level (root, policy, `thresholds`, `actions[*]`) although the schema sets `additionalProperties: false`; the `id` snake_case pattern is schema-only. Default assumption: stay lenient through `0.1.0` and revisit with a spec change if a user hits one. The strict version is `allowIntegerValues: false` on the enum converter, `UnmappedMemberHandling = Disallow` on the serializer options, and an `Enum.IsDefined` check on `ChoiceRule.Action` in `PolicySet.Validate`, each one line plus a `Theory` row.
- **Inbound state extraction. Resolved 2026-09-17.** The middleware and handler used to evaluate the raw body as the state. Roadmap 2.3 introduced `IStateExtractor` with `KassadOptions.StateExtractor` defaulting to `DefaultStateExtractor` (OpenAI chat completions, Anthropic messages, whole body otherwise); the decision above has the shape and `Docs/specs/state-extraction.md` the rules. `RawBodyExtractor.Instance` restores the old behavior.
- **Content outside the last user turn is invisible to inbound policies.** Open. By design of roadmap 2.3, `InboundState` carries the last `user` turn's text and the system prompt only: earlier and assistant turns, tool calls, tool results (`tool` messages, `tool_result` blocks), images and tool definitions are not part of it, so an instruction smuggled in through a retrieved document or a tool result reaches the LLM unjudged, where the raw body would have shown it to the model inside the envelope. Pinned by `Tool_messages_are_not_user_turns` and, live, by the tool-result case in `StateExtractionLiveTests` (Allow). Default assumption: acceptable for `0.1.0`, whose roadmap scopes the fields and whose eval datasets are single-turn; an application that needs the envelope sets `RawBodyExtractor.Instance` or writes an extractor that also emits the tool results; a stage for tool results is `0.2` material. A chat request whose last user turn has no text (tool results only, an image only) is still evaluated whole, so an Anthropic agent loop keeps its tool results visible.
- **Only OpenAI chat completions and Anthropic messages are recognised.** Open. The OpenAI Responses API (`input` / `instructions` / `output[]`), legacy completions (`prompt`), Gemini `generateContent` and the Bedrock/Vertex wrappers are evaluated whole. Default assumption: add a reader when 2.4 or a user needs one; each is one class plus a rule in `DefaultStateExtractor`, listed under "Not recognised" in the spec.
- **Streaming responses.** Passed through unevaluated with a warning. Open until the mechanism lands, after `0.1.0`; designed 2026-09-18 in roadmap 3.4. `Docs/specs/streaming-evaluation.md` compares evaluate-on-complete, chunked windows and post-hoc, recommends chunked windows over the accumulated prefix with trailing delivery, a gated terminal checkpoint and a cut in the provider's own stop vocabulary (the decision above), states the trade-off (TTFT unchanged, last frame one round trip late, exposure bounded at about `max(N, r·t) + r·t` characters rather than zero) and lists 17 open questions with a default assumption each; `Buffer` and gated delivery are the zero-exposure settings. Default assumption until then: no buffering of SSE, as today. Verified by the 2.2 handler tests: the provider's response object goes back to the caller with zero bytes read from its stream, no `Kassad-Outcome` header, the inbound stage still evaluated, and exactly one Warning (`Kassad outbound: streaming response from <uri> passed through unevaluated`).
- **Handler response fidelity.** Open. Three things the 2.2 tests observed and left as they were, because none contradicts `Docs/specs/rejection-response.md`: (a) on an allowed response the `Kassad-Outcome` header carries the outbound stage's outcome only, so an inbound `Review` that passed is invisible to the caller (the middleware exposes its result through `HttpContext.Items`; the handler has no equivalent), pinned by `Outcome_header_reports_the_outbound_stage_when_inbound_was_review`; (b) the handler's synthesized rejections carry no `Kassad-Outcome` header while the middleware's carry `Kassad-Outcome: block`, each as the spec's example for it shows; (c) resolved in roadmap 3.2: an allowed response is now returned from the exact bytes read under every content header the provider sent (`Content-Language`, `Content-Disposition`, `Expires`, ... and `Content-Type` verbatim), pinned by `Allow_keeps_every_content_header_the_provider_sent`; what remains of (c) is that the synthesized rejection's `Content-Type` is `application/json; charset=utf-8` where the spec example shows the bare type. Default assumption: leave (a) and (b) through 2.3 and 2.4 and decide there whether the header should report the more severe of the two stages or split into one header per stage. 2.3 changed only the state the handler evaluates and left (a) and (b) for 2.4. 2.4 decided (2026-09-18, for Jacob's review in PR) to leave both as they are through `0.1.0`: the header is a one-word summary of the stage the component itself evaluated, and the sample shows how an application sees both stages anyway (the middleware's `StageResult` through `GetKassadInboundResult()`, the handler's verdict through the header on the provider's response, a rejected completion through the 403 body); reporting the more severe stage would hide which one fired, and a header per stage or a header on rejections changes the contract in `Docs/specs/rejection-response.md`, a public change that CONTRIBUTING says needs an issue first. Visible consequence in the sample: a `/chat` response whose completion the handler blocked carries the middleware's `Kassad-Outcome: allow` and a 403 `kassad_blocked` body, which `samples/README.md` explains.

## Repository layout

```
/src/Kassad.Abstractions/   contracts only — no dependencies, no serialization attributes
/src/Kassad/                engine; Policies/ (model + JSON loader + validation), Engine/ (resolver, engine), KassadTelemetry.cs (activity source, meter, names)
/src/Kassad.TypeSafe/       HTTP client; SystemOneWire.cs is the only place that knows the JSON shape
/src/Kassad.AspNetCore/     middleware + DelegatingHandler + DI extensions; state extraction (IStateExtractor, InboundState, Default/OpenAI/Anthropic/RawBody extractors over the shared ChatJson reader)
/tests/                     xunit; Kassad.TypeSafe.Tests/Fixtures/ holds recorded wire JSON; Kassad.AspNetCore.Tests hosts the middleware in a TestServer (roadmap 2.1), drives the handler through IHttpClientFactory over a stub provider (roadmap 2.2) and holds ProviderBodies, the OpenAI/Anthropic request and response bodies the extractor tests share with Kassad.TypeSafe.Tests (roadmap 2.3)
/samples/Kassad.Sample.ChatApi/  runnable minimal API; kassad.policies.json is the reference policy file; Llm:Provider selects echo or OpenAI chat completions through the Kassad-wrapped `llm` client (roadmap 2.4)
/samples/README.md               expected responses and log lines from the sample against the live API, in both modes (roadmap 1.3, 2.4)
/eval/                      harness (stub) + datasets/ scripts + results/ (committed JSON); data/ is git-ignored
/schemas/                   JSON Schema for policy files, referenced by $schema in policy documents
/Docs/                      see Docs/README.md
```

`src/`, `tests/`, `samples/`, `eval/` each have a `Directory.Build.props` that imports the root one. Package metadata and analyzers are configured there, not per-csproj. The root `nuget.config` pins nuget.org as the only package source.
